Google Photos AI Discovery Engine — V1
Detailed Product & Technical Problem Statement
1. Project Objective

Build an AI-powered user research and discovery engine for Google Photos.

The purpose of this system is not to build the final Google Photos retrieval solution.

The purpose is to analyze a large volume of publicly available user conversations and identify:

who is experiencing photo-retrieval problems
what they are trying to find
what they remember about the photo
how they attempt to search for it
where the retrieval journey fails
what they do after failure
what workarounds they use
what recurring pain points exist
which user segments experience the problem
which retrieval problems appear frequently enough to investigate through primary research

The output of this system will be used to design 5–6 user interviews and validate the hypotheses generated by the AI.

The system must therefore prioritize evidence, traceability and research usefulness over visual complexity.

2. The User Problem Being Investigated

The overall Google Photos problem is a specific retrieval scenario:

A user knows that a particular photo exists in their Google Photos library, but remembers it only through incomplete or contextual details and therefore struggles to retrieve it.

For example:

"I remember a photo from Goa around New Year. We were having breakfast at a small café. There was a blue wall behind us."

The user may remember:

approximate location
activity
people
visual appearance
occasion
surrounding context

but may not remember:

exact date
exact location
café name
album
filename
exact person
searchable keywords

We do not yet know what part of this retrieval journey is actually causing the biggest failure.

The Discovery Engine exists to investigate that question.

3. Core Discovery Question

The system must ultimately help answer:

Where exactly are users failing when trying to retrieve a vaguely remembered photo, who experiences each failure, and what evidence supports the finding?

The system should investigate the entire retrieval journey:

User remembers a photo
        ↓
User interprets their memory
        ↓
User formulates a search
        ↓
User searches
        ↓
Google Photos returns results
        ↓
User evaluates results
        ↓
User finds the photo
        OR
User tries again
        ↓
User refines / changes approach
        ↓
Success OR abandonment

The system must not assume beforehand which step is broken.

5. Do NOT Collect Everything and Send Everything to the LLM

This is critical.

The raw dataset may contain thousands or millions of conversations.

Most will be irrelevant.

For example:

"Google Photos takes too much storage."

is not relevant to our current research question.

Neither is:

"Google Photos backup is slow."

Neither is:

"I don't like the new UI."

The system must therefore create a relevance filtering pipeline.

6. Relevance Filtering

Every collected record should be classified as:

RELEVANT
POTENTIALLY RELEVANT
IRRELEVANT
Relevant

The conversation contains evidence that the user was trying to find/retrieve a specific photo or memory and experienced difficulty.

Example:

"I know I have a photo from my Goa trip but I can't find it. I've searched Goa and the year but still can't locate it."

Potentially relevant

The conversation discusses Google Photos search or finding photos but does not contain enough detail to confidently classify the retrieval scenario.

These can be retained for secondary review.

Irrelevant

The conversation is about unrelated issues:

storage
backup
pricing
subscription
sync
general bugs
sharing
editing
account problems
unrelated feature complaints

unless the conversation also contains relevant retrieval behaviour.

9. LLM Analysis

After cleaning and relevance filtering, send the relevant records to an LLM for structured extraction.

The LLM should not simply summarize the conversation.

It must extract structured information about the user's retrieval journey.

12. Identify Retrieval Failure Points

The system should classify each relevant conversation into one or more possible failure points.

Failure Point A — Memory Expression

The user has a memory but struggles to describe it.

Failure Point B — Query Formulation

The user describes the memory but doesn't know what terms to search.

Failure Point C — Search Understanding

The user submits a reasonable description but believes Google Photos doesn't understand the context.

Failure Point D — Result Relevance

Results don't contain the expected photo or appear insufficiently relevant.

Failure Point E — Result Evaluation

Too many results make it difficult to identify the correct photo.

Failure Point F — Search Recovery

The first search fails and the user doesn't know how to refine or continue.

Failure Point G — Abandonment

The user eventually stops trying.

The model must also support:

unknown
multiple_failure_points

because not every conversation will clearly identify one failure.

13. Identify User Workarounds

The system should detect how users currently compensate for retrieval problems.

Examples:

manually scrolling through timeline

searching locations

asking another person
using another photo-management tool
creating albums manually

These workarounds are particularly valuable because they show what users are already trying to do to solve the problem themselves.

16. Research Hypothesis Generation

After aggregation, the LLM can generate research hypotheses.

For example:

H1: Users with contextual/experiential memories struggle to translate those memories into effective search queries.

H2: Users may successfully formulate queries but struggle because search results are too broad to identify the intended photo.

H3: Users frequently abandon retrieval after an unsuccessful first attempt because they lack a clear recovery strategy.

H4: Retrieval failure may vary significantly by the type of photo/memory being retrieved.

These hypotheses should always be accompanied by:

supporting evidence count
relevant user examples
source distribution
affected segments
confidence level

The system must clearly label them as hypotheses, not facts.

18. Important: No Premature Solution

The Discovery Engine must not recommend:

"Build a conversational AI."

It should not decide that.

It should only tell us:

"This is where users appear to struggle."

Then we conduct primary research.

After the interviews, we decide what problem is actually worth solving.

Only then do we build the user-facing MVP.

20. Non-Functional Requirements

The application should also:

preserve source traceability
handle large datasets incrementally
support pagination/batching
avoid sending the entire dataset to the LLM at once
support retries for failed LLM requests
avoid duplicate LLM processing
maintain processing status
show errors clearly
allow data export as CSV/JSON
allow new data to be added without destroying existing analysis
maintain source URLs where publicly available
distinguish collected, cleaned, relevant and analyzed records
avoid exposing private user information unnecessarily
21. Most Important Requirement

Do not optimize for a fixed dataset size.

The system should be designed around:

Collect broadly → filter aggressively → analyze relevant evidence deeply.

We may collect:

10,000 → 50,000 → 100,000+ raw records

depending on what the sources support.

The important number is not how many records we scrape.

The important number is:

How much high-quality, relevant evidence about the target retrieval scenario we can identify and trace back to its original source.
